Three test-flakiness cards, one commit each, test-only except for one accounting fix in the usage reader.

## AD-131 — `runtimes::tests::versions_come_from_the_cli_when_asked` under plain `cargo test`

**Cause.** The fixture writes two stand-in CLIs (`#!/bin/sh` scripts) and reads their `--version` through the inventory under its 3 s deadline. On macOS the first run of a new executable file waits on the operating system's assessment of it: about 105 ms on its own, and 0.4–0.9 s measured here while the `installation` and `launch` tests run beside it, since they copy the test binary and run the copies, each a fresh executable to assess; longer still under build load. Plain `cargo test -p agentdocker-host` runs those tests at the same time as this one, so the stand-in's first run queued behind their copies, the deadline passed, and the version came back `None` every round. Under nextest on macOS the configured test group runs one test process at a time, so nothing else was being assessed. Confirmed by running the same test binary in a separate process while only the `installation` or `launch` module ran in another: the stand-in's first run slowed in step; `/bin/sh -c true` (an already assessed binary) never did, and a script's second run takes 4 ms.

**Fix.** `machine()` runs each stand-in once as it creates it, with no deadline, so the assessment is paid before any version is read under one.

## AD-130 — `usage::reader::session::tests::an_unchanged_generation_rehashes_only_its_last_record` on the Windows job

**Cause.** `Session::prepare_next` reported a pass's bytes as what its `Take` handed out (`allowance - limit`). The pass hashes a record at a time through an 8 KiB `BufReader` and checks its deadline between records, so a pass the deadline ends mid-buffer had taken up to 8 KiB more from the file than it hashed; those bytes were counted, then read and counted again by the next pass from `checked`. A proof's passes then summed to more than the prefix by less than 8 KiB per cut pass. The failure seen, 2,335,696 reported for 2,329,090 written (6,606 over), is exactly this shape: 100 ms passes over a 2.3 MB file cut on a slow runner. Nothing Windows-specific is involved (the bytes are written and closed before any read; CRLF plays no part in a byte count); a fast runner finishes each pass's megabyte inside the deadline and never sees it.

**Fix.** The pass reports `checked - from`, the bytes it consumed and hashed, which is what the collector's tally and its debug line already call the bytes rehashed by proofs. New test `passes_cut_by_their_deadline_count_each_byte_once` proves a 2.3 MB prefix in passes cut by a 100 µs deadline and checks they add up to the file exactly; against the old count it fails on every run (shown below).

## AD-80 — `daemon::judge::tests::an_unreadable_tmux_pane_clears_its_judgment` under full-suite load

**Cause.** The test told a hang apart from an answer by a 300 ms capture deadline on every stand-in run, so under load a stand-in still starting was taken for a hang; the AD-125 change already on main gave the answering phases the tests' 10 s bound and left the short deadline to the hanging phase alone. What remained: the hanging stand-in slept 30 s (a clock of its own), and the agent's and the stranger's `sleep 60` children were killed only at the end of the test, so any failure leaked them into the test's output pipes, which is the LEAK nextest reported with the FAIL.

**Fix.** The hanging stand-in writes its pid and blocks on a fifo nothing opens, so the capture's deadline is the only thing that ends it, and after the hanging passes the test checks every stand-in that reached its gate is gone and reaped. The two children are held by an `Owned` guard that kills and reaps them however the test ends, with their output closed.
