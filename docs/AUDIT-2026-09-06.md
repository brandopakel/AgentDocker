# Native product audit — September 6, 2026 (Pacific)

> Historical findings at f66cd3f. Follow-up restore/privacy fixes and current acceptance evidence are tracked in [NATIVE-DELIVERY.md](NATIVE-DELIVERY.md). The reproductions below remain evidence of the audited version.

The product has a substantial native orchestration implementation. Its direction matches the requested bare-metal desktop app with optional engines. It does **not** yet meet the complete experience of installing on any computer, recognizing every active/installed agent, verifying integration health and reliably preserving work across every failure. Two restore defects were reproduced beyond the passing test suite. Correct those and private-state creation before enabling automatic restore or broad real-agent use.

## Blocking findings

### R1 — Restore can spawn after reclaimed-lease persistence fails

**Confirmed on f66cd3f.** In `crates/agentd/src/daemon/restore.rs`, `reclaim_leases` mutates memory and calls `persist`, which latches an error but returns no failure to `restore_one`. `restore_one` then spawns the worker anyway. The new process can write while coordination is disabled and its reclaimed protection does not exist in SQLite.

Reproduction used a disposable repository, private fixture parent and synthetic Python worker. Launch it with `restore: true`, claim its tracked file and cleanly stop the daemon to save a restore point. Add a temporary SQLite `BEFORE INSERT ON leases` trigger that raises `ABORT`, then restart. The worker's start marker advanced, `list` returned `storage_unavailable`, and the durable lease count was zero. All fixture processes were stopped afterward; no real agent was controlled.

Required fix: propagate restore read/write failures, acquire and durably record protection before spawning, stop/reap an owned child if post-spawn registration fails, and preserve the event/persistence contract. Test each failure boundary without allowing a new writer. Audit restore-point deletion/reacquisition as one recoverable transition.

### R2 — Restored workers bypass startup readiness

**Confirmed on f66cd3f.** `crates/agentd/src/lib.rs` calls `restore_agents()` before starting the watcher and before entering the host/restricted socket serving loop. Normal `run` waits for watcher attachment; `restore_one` does not. A restored worker can make its first edit before coverage exists and cannot depend on initial hook/MCP communication.

The fixture's first normal launch could connect to its endpoint. Its normal restored launch recorded that it could not connect on startup. Code order independently establishes that the watcher had not been started. This probe did not claim a quantified missed-ledger rate.

Required fix: restore durable identity/protection first, establish listeners and verified watcher attachment, then permit writers. Add a test whose first action requires coordination and whose first edit must be observed; exercise slow/failed watcher and socket startup too.

### P1 — State and log privacy depends on inherited permissions

**Observed on f66cd3f under the host's normal umask.** A fresh state directory and logs directory were mode 0755; SQLite and the worker log were mode 0644. Socket permissions do not protect those files. Agent specifications can retain explicit environment values, while messages/logs can contain private work. Exposure to another account depends on parent-directory permissions; the audit fixture itself had a mode-0700 parent, so no cross-user disclosure was performed.

Required fix before sensitive daily-use trials: create/validate a user-owned mode-0700 state root and private database/log files, define handling of existing installations, and reject unsafe symlink/ownership cases without touching unrelated data. Bencher credentials are separate and remain private; they were not read into this report.

## Validation and limits

One complete f66cd3f local standard gate passed **377 Rust tests**, five Python installer tests, doctests, formatting, strict Clippy, packaging and release build on Apple Silicon macOS. The final repeat after documentation edits failed at nextest: 376 tests passed and one was marked `LEAK-FAIL`. One explicitly manual socket benchmark test was skipped in each run. All 71 current request operation names have corresponding wire-table rows; this name-level reconciliation does not prove every payload and side effect correct. The two restore probes and file-permission inspection were additional real-process checks.

Two full-suite runs reported leaked output handles after a test body passed and its process exited zero:

- At 90a7597: `agentdocker-core runtime::tests::the_table_is_consistent` (315 passed, one leak failure).
- At f66cd3f with documentation edits: `agentd daemon::working::tests::content_check_catches_unwatched_changes_retries_and_restart` (376 passed, one leak failure).

Both tests passed when run together in a subsequent two-test diagnostic. That does not resolve the full-suite failures or establish their cause. The existing zero-retry policy and 500 ms leak-failure threshold were unchanged; no timeout was relaxed. These are unresolved test reliability findings, not proven false positives or a diagnosed daemon resource leak. Logs of the successful gate, both failures and the targeted diagnostic are retained privately. The final local standard gate is **not green**.

A fresh native GUI smoke at f66cd3f also passed: the app opened with the title `agentdocker`, autostarted an isolated daemon through a long/symlinked home and private fallback socket, automatically discovered a synthetic process without a manual discovery request, and displayed its adopted identity and lease. A window capture confirmed the connected UI. The GUI process had no TCP sockets. Only the test-owned process was adopted; existing agents were merely visible in discovery. The fixture window, daemon and worker were stopped afterward.

Existing Linux/macOS CI, engine tests and historical bundle smoke results provide separate evidence. They are not substitutes for Windows, Linux desktop, Intel runtime, long-session, sleep/wake, installed upgrade, real provider, or multi-host tests. No engine VM, account enrollment, real-agent adoption or user integration config was needed for these audit probes. See [LOCAL-TRIAL.md](LOCAL-TRIAL.md) for the staged test plan.
