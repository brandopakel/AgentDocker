AgentDocker audit — September 4, 2026 (Pacific time)

The implementation contains the Phase 0–2 feature set, but it is not yet ready to claim reliable coordination in every supported case. The most consequential gaps are inconsistent resource identity, process lifecycle handling, cancelled claims, and installation verification. Phase 3 is the right next product milestone after those foundations are hardened.

This review is anchored to commit `a359b466bcc336904490554387abc75b68118cd9`, on `feat/vcs-report`. It covers the four Rust crates, adapters, service/packaging code, README, architecture, roadmap, and GitHub PR state. During the audit another process began adding `notify` and `ignore` dependencies, then Phase 3 watcher/change types and daemon/store/protocol edits to the working tree. Those uncommitted Phase 3 edits are outside this snapshot; the auditor did not modify them. This is a review, not a certification or a completed bug-fix pass. Source line references below refer to the audited commit.

Validation: `cargo fmt --all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo build --workspace`, and all 110 existing workspace tests passed on the audited baseline. The process-discovery test failed inside the sandbox and passed outside it. Separate reproductions used a temporary daemon/database and synthetic processes; these were stopped afterward. Installer verification used a mock download and installed only inert scripts into a temporary directory. No existing agent, service, GitHub PR, or user installation was changed.

Findings requiring implementation work

1. **P1 — exclusive leases can fail to conflict on the same physical resource. Reproduced.** `crates/agentd/src/daemon.rs:1182` chooses a file key partly from the holder's project. In a plain directory, its member claims `x` as `file:<project>/x`, while an outsider claims the exact same physical file as `path:<absolute>/x`; both exclusive claims succeed. A second case exists at a repository/Agentfile root: discovery starts from `path.parent()`, so an outsider's whole-root claim remains a raw path and does not block an existing project file lease. Querying that root also misses the project file lease. This contradicts the directory-protection and path-query contracts. Make physical identity consistent across callers, including root directories, plain directories, and aliases, while keeping logical cross-worktree overlap a separate concept. Regression tests should cover both reproductions and queries with and without an agent filter.

2. **P1 — stopping an adopted process releases protection before the process exits. Reproduced.** In `daemon.rs:720`, an unsupervised process is signalled and immediately passed to `mark_exited`. A synthetic process that ignored SIGTERM remained alive while `stop` returned `exited` and its leases became empty. A process handling SIGTERM slowly has the same race. Track a stopping state and retain leases until exit is observed, with bounded escalation where appropriate. Managed process trees also need a defined shutdown policy: the supervisor starts one child, and stopping currently signals that PID rather than a dedicated process group.

3. **P1 — signal targets are not validated on the stop path. Static finding; dangerous signals were not executed.** `register` at `daemon.rs:439` accepts a `u32` PID; `stop` casts it with `pid as i32`. Zero and out-of-range values can denote process groups or broader signal targets. The existing bounds check is inside `process_exists`, used by liveness/adoption, and does not protect a stop before the next liveness tick. The stop path also omits the start-time comparison used by liveness, leaving a recycled-PID window. Use checked positive PID conversion and process-identity checks at every signal boundary, including shutdown. Test target selection through a mock signal interface rather than sending broad signals.

4. **P1 — the installer installs an archive after checksum failure. Reproduced.** `install.sh:37` combines download and verification into an `&& … || echo` expression. A mismatching checksum reaches the same “no checksum to verify” branch as an unavailable checksum and installation continues. A valid test archive with an all-zero checksum printed a mismatch, installed both inert binaries, and exited 0. Separate retrieval from verification and abort on mismatch before extraction or replacement. Test valid, missing, malformed and mismatched checksum cases, including preservation of an existing installation.

5. **P2 — cancelled or finished claimants can acquire leases. Reproduced.** `daemon.rs:1022` resolves historical as well as live agents without checking liveness. Register → deregister → claim succeeded. Separately, a waiting socket was closed, the holder released, and the disconnected waiter still acquired a five-minute lease. `server.rs:82` awaits a unary handler without observing disconnect. Validate liveness at acquisition, including after awaits/retries, and make waiting requests cancellation-aware. Claim admission and exit cleanup need an ordered state transition so a check alone does not introduce another race.

6. **P2 — ordinary claim/renew can remove expirations without durable cleanup or expiry events. Static finding.** `crates/core/src/lease.rs:239` and `:289` call `expire(now)` and discard its returned leases. If those paths expire a lease before the daemon reaper, the reaper can no longer delete its stored row or emit `lease_expired`. Waiting requests may miss the expiry wake-up and storage accumulates stale rows. Return expiration effects to the daemon or centralize expiration so all mutation paths persist and announce them. Add a deterministic test where claim/renew wins the race with the reaper.

7. **P2 — release packaging is unfinished. Reproduced manifest failure.** `cargo package -p agentdocker --no-verify --offline --allow-dirty` fails because the internal `agentd` dependency has no version requirement; workspace path dependencies similarly need publishable versions. The Homebrew formula contains four zero SHA-256 placeholders. Add internal versions, publish dependencies in order, populate the formula from actual release artifacts, and exercise installation on a clean machine. A successful source build does not establish that the README's public installation routes work. Public registry/release availability was not independently certified here.

8. **P2 — hook timeouts and messaging guarantees need narrower contracts. Static findings.** `hooks.rs:97` bounds daemon startup, but `client.rs` has no response-read timeout and `hooks.rs:110` has no overall deadline. A listening but unresponsive daemon can stall the hook until the host's configured timeout (15 seconds in the installed entries), rather than the intended short fail-open path. Use a hook-wide budget. Also, inbox drain/subscribe removes messages before network delivery is acknowledged, while stream lag at `server.rs:130` is only logged by the daemon; the client is not actually told it skipped messages as the architecture claims. Keep existing at-most-once live delivery explicit; add acknowledgements for future reliable handoffs/questions instead of assuming the current drain operation proves delivery.

Before the journal relies on persistence, address concurrency ordering too. Memory mutation, SQLite writes, sequence allocation and event publication occur under separate locks. For example, an inbox drain can remove memory state, a concurrent send can enqueue and persist a new message, and the drain can then clear that new row from SQLite. Likewise, an older agent snapshot can be persisted after a newer snapshot. `emit` allocates a sequence separately from persistence/publication, so concurrent callers can publish out of sequence. These are static interleaving risks, not reproduced stress-test failures in this audit. A serialized mutation path or explicit ordered transaction/effect model is preferable to scattered checks; preserve the core's pure logic.

Architecture decisions to settle before their dependent features

| Decision | Current inconsistency or missing rule | Recommended resolution |
|---|---|---|
| Physical checkout versus logical project path | Phase 2 intentionally makes worktrees share `file:` keys; Phase 4 says their absolute path keys never collide | Represent checkout identity for write exclusion, project-relative identity for overlap analysis, and project-scoped branch identity for integration |
| Watcher coverage and freshness | A project root watch does not cover linked worktrees outside that root; a branch/HEAD is not a version of uncommitted content | Watch active checkout roots and relevant Git metadata; use content hashes or observed per-file generations; distinguish another branch's change from invalidation of this checkout |
| Release/journal ordering | Journal write path still iterates `path:` resources; actual project leases are `file:`. A release can precede the 100 ms debounced change reaching the ledger | Translate stored resources directly and establish an observation barrier or pending finalization before deriving the release entry; retain the planned transactional coupling |
| Git movement and attribution | Journal design labels a ref move “committed”; checkout, reset and rebase also move refs. Exclusive lease ownership is evidence of intent, not proof of authorship | Classify movements and keep observation, inference and confidence explicit; preserve source evidence for attribution |
| Container authority and paths | Giving a sandbox a token does not make it use one if the same socket also accepts token-free trusted requests; host canonicalization cannot interpret a container-only `/work` automatically | Provide an authenticated endpoint/proxy unavailable as a token-free control path, with a registered mount/checkout mapping; enforce identity on every operation before forwarding |
| Durable handoff | Sending then releasing/transferring leases and advancing cursors needs failure semantics | Introduce a handoff ID, recipient acknowledgement and retry/idempotency rules; commit ownership changes at a defined acceptance point |
| Budgets and federation | TTL reservations bound outstanding quantity, not cumulative money/token spend; independently writable daemons cannot guarantee global exclusivity merely by exchanging leases | Separate reservation from settled usage; choose authority, fencing and partition behavior for distributed resources before federation implementation |

These are design changes, not reasons to abandon the architecture. Rust core/host/daemon/client separation is appropriate; derived grouping, adapter-driven observation, bounded digests and explicit best-effort attribution are coherent choices. The next layer needs stronger invariants than the current implementation provides.

Documentation corrections

The README still labels MCP “planned” in its diagram, says “Three crates,” and omits `crates/host` from that list. Its MCP-only example claims sessions “will refuse” conflicting edits, although MCP merely exposes voluntary tools; automatic denial exists only for the covered Claude hook edit tools, and those hooks deliberately fail open. Shell/script writes are not covered by that matcher. Describe visibility, messaging, observation and enforcement separately for each adapter.

The architecture introduction says everything after Phase 1 is design intent even though Phase 2 sections are marked done. Its security section discusses per-agent tokens in Phase 6, while the settled plan puts them in Phase 4. Its isolation and journal paragraphs retain the obsolete `path:` assumptions described above. Mark implementation, merged-to-main, and publicly released status separately. Use measured performance numbers instead of asserting “costs nothing,” sub-millisecond execution or fixed memory cost before those paths have benchmarks.

Product direction

The recommended initial audience is developers running several coding agents on one repository. This is an assumption pending the user's product preference. The promise should be concrete: **agents know when their working assumptions became stale, and a replacement session can safely continue with an evidence-backed handoff.**

Messaging and reservations alone are already covered by [MCP Agent Mail](https://github.com/dicklesworthstone/mcp_agent_mail), whose documentation describes agent identities, inboxes, searchable conversations and advisory file leases. [Agent Orchestrator](https://github.com/Untrivial-ai/agent-orchestrator/blob/main/README.md) already documents a local daemon, isolated branches/worktrees and unified agent/PR/CI supervision. [LangGraph](https://docs.langchain.com/oss/python/langgraph/overview) provides durable execution and human oversight for authored agent workflows. These primary sources were checked during the audit; this is a focused comparison, not an exhaustive market survey or a uniqueness claim.

My inference is that AgentDocker should earn differentiation through the correctness and portability of its observed working state. Prioritize these extensions:

| Capability | User value | Minimal useful implementation |
|---|---|---|
| Freshness checks with evidence | Avoid an edit based on a file another agent changed | Read observation + content version + author evidence + reread requirement; show why an edit was blocked |
| Validation tied to the exact code tested | Stop carrying forward “tests passed” after relevant code changes | Store command, exit status, checkout/HEAD and dirty-content identity; mark the result stale when its inputs move |
| Verified session handoff | Recover from a closed/crashed session without reconstructing everything manually | Bundle changes, checks, unread messages, decisions and unresolved blockers; acknowledge receipt and revalidate state before applying it |
| Adapter capability and health reporting | Make partial integration visible | Report discovered/registered/message-capable/read-observed/write-guarded status, plus an end-to-end `doctor` check |
| Conflict explanation and attention view | Help the human intervene where useful | Derive stale readers, conflicting writers, lost observation and failed checks from the ledger/events; show these before building a broad dashboard |

A small decision/constraint record complements automatic observation: filesystem events cannot infer why a design was chosen or which user decision remains open. Treat explicit rationale as attributed input, linked to affected changes, rather than inventing explanations from edit activity. Later, symbol/dependency impact analysis can catch conflicts across different files; it should follow a measured, reliable file-level implementation.

Suggested delivery sequence: harden the reproduced safety/lifecycle issues and release path; settle checkout identity and mutation ordering; deliver one complete Phase 3 scenario (A reads, B writes, A is warned and must reread); add durable journal/recovery and validation evidence; then worktree integration and authenticated container support. Keep large orchestration policy and federation behind demonstrated local demand. Pull a minimal human escalation path forward if it is needed to resolve real conflicts.

Acceptance should be behavioral: two aliases of one physical file never get simultaneous exclusive protection; cancelled or exited agents acquire no new leases; a live stopping process retains protection; every expiration has one durable effect/event; a checksum mismatch never installs; an acknowledged handoff survives restart; two isolated checkouts can edit independently while logical overlap remains visible. Measure missed stale edits, false alerts, notification latency, hook delay and context injected per session. These outcomes are the basis for claiming a distinctive, dependable product.
